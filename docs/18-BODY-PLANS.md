# 18 · 身体方案（Body Plans）—— 目前最大的设计缺陷与解法

> 记录时间 2026-09-12。项目负责人的原话：
> 「现在做的每一款机器人都有些雷同，而且形体上没有真正跟其他不一样的。
> 在我们骨架下面 unit 起来的都是人形的，没有新意。」
>
> **这个判断是对的，而且是架构造成的，不是素材质量造成的。**

## 1. 病因

现在的表达方式只有一种：

```
人体骨架（17 根骨头）→ 每根骨头挂一个刚体部件 → 渲染
```

于是不管选哪个条目，观众看到的都是**同一具人体，换了一身皮**。
`orb`（球）、`furball`（毛球）、`patrol`（四足机）这三个条目尤其荒唐 ——
它们在物种谱系里的全部意义就是「不是人形」，而我把它们做成了穿着相应涂装的人形。

更深一层：**"一根骨头一个刚体件"这种表达本身就读作"手办"**。
原作《Future You》里的形体是流过身体的**物质**（团块、带状、毛、粒子），
不是"头部件 + 手臂件 + 腿部件"。所以我们既不像参考的机器人公司，也不像原作 ——
因为我们复刻的是它的**交互**，没有复刻它的**表达**。

还有一条关于"像不像某家公司的机器人"的：
**辨识度住在整体剪影里，不在零件里。** 一段 Spot 的小腿不会让人认出 Spot。
把一个物种拆成 10 个槽位件去生成，等于先把辨识度扔掉再去追求它。

## 2. 解法：身体方案是可插拔的，和玩法一样

```
Skeleton（永远是人体 —— 站在那里的确实是个人，这是输入，不该改）
      ↓
BodyPlan：把这具人体骨架翻译成「这个物种的身体」
      ↓
Renderable（刚体实例 / 粒子 / SDF 团块 / 带状 / …）
```

分两档，**第一档几乎不要新代码**：

### A 档 · 骨架重映射（纯函数，在 core 里，可单测）

`remapSkeleton(sk, plan) → Skeleton`。输出还是 17 根骨头，交给现有的刚体渲染器，
**一行渲染代码都不用改**。

| plan | 改的是 | 做什么 | 观众看到 |
|---|---|---|---|
| `rig` | — | 恒等映射（现状） | 人形 |
| `quadruped` | **拓扑** | 躯干转成水平；双臂变前腿、双腿变后腿；头从胸前伸出 | **一只四足机器兽**。你抬手 → 它抬前腿 |
| `radial` | **拓扑 · 开发预览** | 没有脊柱也没有四肢链：四条肢摊到四条绕核心的轨道弧上 | **一个笼子绕着一个核心**。你张开双臂 → 环扩大。未系住承重链，暂不进入自动旅程 |
| `column` | **拓扑** | 没有腿：六块腿骨串成一根从地面长上来的桅杆，双臂是顶端的分支 | **一根会折叠的柱子**。你蹲下 → 柱子折起来 |
| `inverted` | **拓扑** | 上下颠倒，手当脚，按整体最低点着地 | 倒立行走的东西 |
| `towering` | 比例 | 四肢按 1.55× 拉长、躯干压扁 | 瘦高的巨人 |
| `stub` | 比例 | 四肢压到 0.55×、头放大 | 矮胖的小人 |

**"改比例"和"改拓扑"是两件事，别混着说。** `towering` / `stub` 只动数字 ——
把一个本来就该不是人的条目设成 `towering`，得到的只是一个被拉长的人。
真正换物种的只有上面标粗的那四条。这一点是 2026-09-13 那一轮的起因：
`xeno`（异形）、`orb`（球）、`furball`（毛球）当时全都只挂着比例，所以全都还是人。

四足那条是投入产出比最高的：它是**纯坐标变换**，但观众一眼就知道"这是另一个物种"。
而且它保留了交互 —— 你抬手，它抬前腿，因果链没断。

#### A 档的那条铁律

`quadruped` 立的规矩，后面每一个新拓扑都必须守住：

> **保留肢体的世界量，只换插座。**

四足是"四肢的世界方向原样保留，只把肩/胯搬到水平躯干上"；
`column` 是"双臂的世界方向原样保留，只把肩搬到桅杆顶上"；
`radial` 换了一种量但是同一条道理 —— 保留的是**每条肢伸出去多远、末端多高**，
把它们变成那条弧的**半径**和**高度**。

守住它，"我抬手，它就…"这句话才说得出来。守不住，就只是换了个模型。

#### `radial` · 无躯干型（适合 `orb` / `furball`）

```
        ╱‾‾‾╲          四条轨道弧，各自倾斜，合起来是一个笼子
   ╱‾‾‾╲ ● ╱‾‾‾╲       ● = 核心（脊柱+颈+头压到 0.40）
        ╲___╱          两条锁骨自动变成核心到环的系绳
```

- **没有脊柱**：核心被压到人体躯干的 0.40，居中悬在笼子里 —— 不压的话读作"躯干 + 一个环"。
- **没有四肢链**：每条肢的三块骨头排成一条圆弧，**弦长 = 骨长**，所以部件一件都不被拉伸。
  还白捡一条读法：半径小的时候同样的骨长要绕更多角度，笼子自己盘紧；张开时松开。
- 因果：**半径 = 末端离身体中心多远**（张开双臂 → 环扩大；蹲下 → 环收拢）；
  **高度 = 末端相对中心的高度**（抬左手 → 左前那条弧整条浮起来）；
  **朝向 = 肩轴**（人转身 → 笼子跟着转）。
- 两条腿的弧没有骨头连回核心，所以它们真的浮着。这是旧实验的明确选择，但真实观众会读成
  腿与身体断开，因此现在只能用显式 `?plan=radial` 做开发预览。物种声明仍保留，
  自动弧线由 `app/src/creature/body-plan-policy.ts` 退回连通人形；现场控件和随机池同样不暴露它。
- 落地基准换成**整体最低点**（`PLANS_WITHOUT_FEET`）：这具身体上"脚"已经没有意义，
  按脚贴地会让半个笼子沉到地板下面。

#### `column` · 单柱型（适合 `manipulator` / `screenface`）

```
      ○        头（沿人的头向，唯一的朝向线索）
     ╱│╲       双臂 = 顶端的分支，世界方向原样保留
      ╲        脊柱也参加之字 —— 立直了会被读回"半个人"
      ╱
      ╲        桅杆：footR→shinR→thighR→footL→shinL→thighL 首尾相接
      ╱
   ───┴───     地面
```

- **没有腿**：右腿顶 = 左脚底，左腿顶 = pelvis，人体骨架里那两处本来就没有骨头相连，
  重合就是把缝合上。结果是 17 根骨头一根不多一根不少，仍然是一具合法 `Skeleton`。
- **蹲下 = 折叠**，不是压缩：每一节交替倾斜，倾角 = `baseLean + 蹲的程度 × foldLean`。
  为什么不直接缩短：骨长就是部件的长度，缩短会把部件压扁；折叠只改方向不改长度，
  部件一件不变形，高度一样会掉下来。
- 因果：抬手 → 分支抬起；张开 → 分支张开；蹲下 → 柱子折起来变矮；转身 → 折叠平面跟着转。
- 柱子比人高（1.7m 的人 → 约 2.6m 的桅杆）。这是对的：两条腿串起来本来就该长。

#### 比例与拓扑的先后

| kind | 顺序 | 为什么 |
|---|---|---|
| `quadruped` / `inverted` | 先拓扑，再比例 | 它们保留了"肩是肩、胯是胯"，`proportion()` 照常成立 |
| `radial` / `column` | **先比例，再拓扑** | 这两个拓扑把人体语义拆了；拓扑之后再缩放会把环和桅杆撕开 |

所以 `{ kind: 'column', arm: 1.45 }` 的意思是"先把这个人的手臂拉长，再让他变成一根柱子"。
效果一样直观，而且 `proportion()` 始终作用在一具还是人的骨架上。

### B 档 · 换一种表达（新渲染器，实现同一个 `BodyInstance` 接口）

| plan | 表达 | 对应条目 |
|---|---|---|
| `mass` | 关节处放 metaball，SDF 融成一个连续团块 | coral / xeno / char.dumpling |
| `swarm` | 点被骨线吸引，**每个点落后的时间不同** | field ✅ 已落地 |
| `ribbon` | 沿骨链的带状面片 | char.ghost / softwear |
| `orb` | 只有一个球在身体质心，按运动能量形变；手脚位置放小卫星 | orb |
| `fur` | 骨线上长壳层（shell fur） | furball / petbot |

B 档才是真正接近原作表达的那一层。`mass` 应该最先做 —— 它一个人就能把
coral / xeno / dumpling 三个条目从"手办"变成"物质"。

#### `swarm` · 点场（适合 `field`）

```
   · ·  ·        点锁在骨头上，但**每个点落后的时间不同**
  ·:·. ·  ·      站住 → 所有时刻重合，形短暂地回来
 · ·:·::. ·      一动 → 沿轨迹拉开，只剩运动
   ·· ·  ·
```

- **不是新渲染器**：复用 `app/src/stage/particles.ts` 的呼吸粒子团 ——
  同一批公告牌、同一段衰减/加色/呼吸、同一个 draw call。
  变的只有「聚拢位置」：从一副写死的 tier 0 站姿，换成**这一帧和前 0.5 秒的真骨架**。
  空场的那团雾和这具身体因此是同一种材料，进出场就用它本来就有的 `gather`
  （`gather = pres`）：进场是地面的雾聚拢成这个人，离场是散回地面。
- **怎么做到每帧不写大数组**：上传的是**骨架**不是点。一个 16 格的环，每格
  17 根骨头 × 2 端点 = 34 个 vec3，按 `SWARM.trailStep`（35ms）**定速**推进
  （不是每帧一格 —— 每帧一格的话拖影时长会随帧率变）。点在顶点着色器里
  按自己的延迟去环里插值取位置。每帧 CPU = 34 次 `Vector3.set` + 几个标量。
- **延迟的分布才是这条线的全部**：`rand^SWARM.lagCurve`（2.4）把多数点压向"现在"，
  少数拖在后面。给 1（均匀）得到的是一条等厚的糊带 —— 那读作"运动模糊"，
  不是"只剩运动"；给 0（全部锁死）得到的是**一具点描的人**，形还在，只换了笔触。
- **延迟不沿骨链再排一次**：`vitality.ts` 已经在骨架那一层做过 root→tip 的跟随
  （末端比根部慢半拍），这里再来一遍，手会拖出比脚长一倍的尾巴，读作"手很重"。
  这一层分配的是**另一个轴** —— 同一根骨头内部的时间厚度。
- **落地是它自己的事**（和 `mass` 同一个坑，第三次）：骨架层只保证最低的**关节**
  在 y=0，点撒在骨头周围，踝在 y=0 时脚那一段的点有一半在地板下面。
  量法是**逐点**（`core/swarm.ts` 的 `lowestSwarmY`），不是"骨头最低点 − 抖动半径"——
  后者是包络，1400 个点里落在包络角上的可能一个都没有，按包络落地会让
  看得见的那片点浮在空中一层抖动半径。

#### `mass` 还兼着另一份差：**所有物种的 tier 0**

`assets/parts/parts.json` 里 tier 0 的部件数是 **0**（198 件全在 tier 1/2），
而演化从 tier 0 起步。于是"观众看到的第一具身体"每个槽位都退到 `library.ts` 的
兜底几何 —— 方块躯干 + 胶囊四肢 + 球头 + 楔形手脚。

**那不是一个形态，那是一个 catch 块。** 它的职责是"资产没到货时也别崩"（ADR-4 / P3）。
拿它当开场，按 `docs/26 §E` 的判据，观众读到的是"它坏了"，不是"它还没认出你"。

所以 tier 0 应当**一律走团块**，tier ≥ 1 才切到刚体件（`app/src/creature/nascent.ts`）：

- 参数比常规团块更融（`NASCENT.radiusScale` / `slotScale`）—— 四肢不是四条管子，
  是一个还没分化出零件的连续的体。头反而要**放大**，否则唯一的朝向线索被躯干吞掉。
- 升档那一刻刚体先冒头、团块后退去（`NASCENT.leadIn`），两者重叠的那几帧
  就是"零件从团里顶出来"。时长 `NASCENT.emerge` **等于** `STAGE.pulseDuration`，
  因为 `stage.pulse()` 的亮度脉冲必须和形态变化同一拍。
- `bodyPlan: 'mass'` 的条目本来就全程是团块，不经过这一层。

副作用是 tier 0 从 30 实例 / 15k 面 / 11 draw 降到 **0 实例 / 2k 面 / 1 draw**。

> ✅ **这一条现在是开着的**（`NASCENT.enabled = true`）。它曾经因为下面那件事被迫关掉，
> 那件事已经修了。

#### 团块方案曾经从来没有跑到过帧率（已修，2026-09-13）

**根因一句话：`Mesh.count` 是 three 自己的实例数字段，而 `MarchingCubes` 这个 addon
把同一个字段当"这一帧写了多少顶点"在用；`three/webgpu` 取实例数时只认字段名，
于是整具团块每帧被实例化了几千份。**

- `RenderObject.getDrawParameters()`：`else if (object.count !== undefined)
  instanceCount = Math.max(0, object.count)` —— 它不问这个 Mesh 是不是 `InstancedMesh`。
- `WebGLRenderer` 走的是 `object.isInstancedMesh` 分支，所以同一个 addon 在 WebGL 上没事。
  **这是 WebGPU 后端独有的字段名冲突**，不是 addon 到处都坏。
- 症状因此长得很反直觉：1 个 draw call、2k 面，而 `renderer.info` 里一帧 **1200 万面**。

修法（`app/src/creature/mass.ts`）：`MarchingCubes` 只当**几何发生器**用，**不进场景图**；
场景图里放一个共用它 `geometry` 的普通 `Mesh`，那个 Mesh 的 `count` 老老实实是 1。
一行改动，不加依赖，不碰 res。

实测对照，同一台机器、同一分钟，`?demo=1&theme=<id>&tier=2&debug=1`，
rAF 计数 4 秒 × 3 轮（方法见 §7）：

| 物种 | 修前 rAF fps | 修后 rAF fps | 面 / draw |
|---|---|---|---|
| `coral` | 5.5 | **42–46** | 2.3k / 1 |
| `char.dumpling` | 6.0 | **43–50** | 2.3k / 1 |
| `char.ghost` | 7.6 | **48–51** | 2.2k / 1 |
| `porcelain`（刚体对照） | 37–39 | 37–39 | 87k / 30 实例 / 18 draw |

`/dev/mass.html?res=36`：**8.7 → 99.2 fps**，`renderer.info` 提交面数 12,600k → 2.0k。

**为什么它在眼皮底下待了这么久**：团块的 HUD 报的是毫秒，而毫秒一直很好看
（JS 每帧 1.2–2.4ms，主线程 93% 空闲 —— 时间全在 GPU 提交那一侧）。
只有 fps 那一行会说实话，而 dev 页的 fps 当时**没有颜色**；§7 的取证配方拍的又是
**静帧**，静帧里看不出帧率。三件事凑齐，一个 8 倍的帧率洞就是看不见的。

现在钉住它的有三样，缺一不可：

1. `BUDGET.minFps`（55）+ 两个 HUD 都把低于它的 fps **整行标红**
   （`shell/hud.ts`、`dev/mass.ts`）。
2. `dev/mass.html` 的 HUD 多报一行 **`提交 Xk 面/帧`**（`renderer.info.render.triangles`）。
   它和团块自报的 `三角 N` 对不上，就是有人在偷偷实例化 —— 这次的根因一眼可见。
3. `packages/app/test/mass-instancing.test.ts`：断言场景图里可画对象的 `count === 1`、
   且没有 `isMarchingCubes`。**故意不断言帧率** —— 帧率断言在 CI 上必然不稳，
   而"实例数是不是 1"是同一件事的确定性表述。

## 3. 接口

```ts
interface BodyPlan {
  id: string;
  /** 需要什么资产：slots = 10 个槽位件；monolith = 整体件；none = 纯程序化 */
  assets: 'slots' | 'monolith' | 'none';
  /** A 档只实现这个：纯函数，输入输出都是 Skeleton */
  remap?(sk: Skeleton): Skeleton;
  /** B 档实现这个：自己拿骨架去渲染 */
  create?(ctx: BodyContext): BodyInstance;
}
```

`RosterEntry` 增加 `bodyPlan: string`（默认 `'rig'`）。
A 档条目只填一个字段就换了物种；B 档条目需要一个新模块。

## 4. 还有一条：`monolith` 资产模式

对**需要辨识度**的条目（四足机、无人车、宠物机器人），不要拆 10 个槽位件去生成，
而是：

1. 一次生成**整只**（`TAPose` 之类的参数配合，或者干脆就是一整只动物的造型）；
2. 离线切成 4–6 个大块（躯干 / 四肢 / 头），切口在关节处；
3. 这几块仍然走同一套挂载契约（主轴 +Y、socketA 在原点、长度 1）。

代价是多一步离线切分，收益是**剪影是对的**。
辨识度住在剪影里，这是唯一能拿回它的办法。

## 5. 为什么现在才发现

因为我先把管线、契约、编排做扎实了，而这些都是**跟表达无关**的层。
管线越顺，越容易在"多生成 100 件"上感到进展，而真正的问题是
**我们只有一种表达**。这是一个典型的：工程指标全绿，作品没成立。

记在这里，是为了下次别再用"再生成一批素材"去回答一个表达层的问题。

## 6. 谁用哪个方案（2026-09-13 重新分配之后）

权威在 `packages/factory/recipes/roster.ts` 的 `BODY_PLAN`，这里是它的读法。

| 方案 | 条目 | 为什么是它 |
|---|---|---|
| `rig` | porcelain · industrial · athlete · softwear · char.idol · guest.founder · **digitigrade** | 需要有一个人形基准，否则"不同"就没有参照。digitigrade 是 2026-09-13 从 `quadruped` 挪回来的：Digit 和同拓扑的 Cassie 都是**两足**，做成四足，"人的手 / 鸟的腿"这句 tagline 就没有对比了（docs/31 §4.1） |
| `quadruped` | patrol · wheelleg · petbot · **autonomous** | 无人车不是"会走的车身"，是一个贴地底盘 —— 四个短支撑比两条腿准 |
| `radial` | **orb** · **furball** | 它们仍声明这个目标，但当前自动旅程会退回保留身材参数的连通人形。系绳 + 真人验收过门后才恢复自动到场 |
| `column` | **manipulator** · **screenface** | 共同点是"底盘 + 上面一套作业机构"，本来就不该有腿 |
| `inverted` | **xeno** | 它的 tension 是"它在模仿你，但模仿错了"。把人整个翻过来正是"模仿错了" |
| `swarm` | **field** | 它的 tagline 就是「身体消失，只剩运动」，而在这之前它挂着 `rig`、向别的物种借了一整套四肢 —— 屏幕上说的话和自己写的话正好相反。它是全 roster 唯一 `source:'procedural'`、自有部件为 0 的条目，所以 B 档在这里**不作废任何资产**（§8 第 3 条那条顾虑对它不适用） |
| `mass` | coral · char.dumpling · char.ghost | 它们的 tension 本来就不是"机器"，手办式刚体件是它们最不该有的读法 |
| `stub` | compact · droid | 它们**就是**"人形，但只有一米三" —— 这里比例才是对的答案 |
| `towering` | char.paper | 折出来的东西本来就该又高又薄 |

加粗的六个是这一轮从"人形挂零件"挪走的。挪之前它们全都只挂着比例。

### 挪走之后，它们原本的刚体部件怎么办

**一件都没浪费。** 这是选 `radial` / `column` / `inverted` 而不是 `mass` 的主要理由：

- A 档的输出仍然是一具合法 `Skeleton`，仍然是 17 根骨头一根挂一件 ——
  `orb` / `furball` / `manipulator` / `screenface` / `autonomous` / `xeno`
  这六个条目的部件（xeno 20 件 full，其余各 6 件 light，合计 **50 件**）照常被实例化。
  变的只是这些件被摆在哪里。
- 真正会作废部件的是 **B 档**：`bodyPlan: 'mass'` 的条目一个槽位件都不实例化。
  现在挂着 `mass` 的三个（coral 20 件 / char.dumpling 6 件 / char.ghost 6 件，共 32 件）
  确实在"花过 credits 但画面上看不见"的状态里 —— 那是 mass 落地那一轮就做出的取舍，
  这一轮没有扩大它。
- 一度考虑过把 `furball` 也挪到 `mass`（"毛球"本来就该是一团）。**没有挪**：
  radial 用它自己的 6 件就能拿到"不是人"的读法，而 mass 会让那 6 件直接作废。
  一个零成本的方案和一个要作废 6 件的方案给出同一个结论时，选零成本的那个。

### 帧率怎么量（**静帧不会告诉你它多久才出一帧**）

上面那套拍的是静帧。静帧看不出帧率，而 B 档方案最容易坏的恰恰是帧率 ——
`mass` 曾经以 1 个 draw call、2k 面的成绩跑在 6 fps 上（见 §2「团块方案曾经……」）。
**给任何 B 档方案取证，必须另外做这一条。**

1. **用 rAF 计数，不要看 HUD 的毫秒。** 毫秒说的是"我们的 JS 花了多久"，
   帧率说的是"画面多久换一次"。GPU 那一侧停住的时候，两者可以差一个量级。
   开 `?debug=1`，在控制台跑：

   ```js
   // 量 4 秒里真正出了多少帧。跑 3 轮取范围，不要只跑一轮 ——
   // 开发机上同一配置轮次之间能差 1.5 倍。
   const fps = (ms = 4000) => new Promise((res) => {
     let n = 0; const t0 = performance.now();
     const tick = () => { n++; const d = performance.now() - t0;
       d < ms ? requestAnimationFrame(tick) : res(+(n / (d / 1000)).toFixed(1)); };
     requestAnimationFrame(tick);
   });
   await fps();   // 先让页面跑满 ~9 秒再量：EMA 要收敛，demo 片段也要进入稳态
   ```

2. **对照组是刚体路径，不是"感觉还行"。** 同一台机器、同一分钟内量
   `?demo=1&theme=porcelain&tier=2&debug=1`。团块比它低一个量级就是 bug ——
   团块的面数和 draw 都少一个量级，**它没有理由更慢**。

3. **看 `renderer.info.render.triangles`，不要只看我们自报的三角数。**
   `/dev/mass.html` 的 HUD 已经把它报成 `提交 Xk 面/帧`。两个数对不上，
   说明有人在偷偷实例化或者 `drawRange` 没收住 —— 自报的那个数是我们算的，
   提交的那个数是真的。

4. **fps 低于 `BUDGET.minFps`（55）时两个 HUD 都会整行标红。**
   截图取证时**必须把 HUD 一起拍进去**，红的那一行就是结论。
   见 `scratch/evidence/mass-hud-red-before.png` / `mass-hud-green-after.png`。

5. headless（`--virtual-time-budget`）下的 fps 和毫秒都**不是**真实读数 ——
   虚拟时钟会把它们拉平。headless 只用来拍 HUD 的**颜色**和**提交面数**，
   帧率数字一律以交互式 rAF 计数为准。
